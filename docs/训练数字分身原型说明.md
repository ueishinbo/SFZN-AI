# 历史讨论稿：训练数字分身原型说明（单岗位 role 方案）

> 状态：已被替代，保留日期：2026-09-09。本文记录早期 `role / soul / memory` 与“一人一个岗位 role”的讨论，不是正式 PRD，也不代表当前 Demo 或产品规则。
>
> 当前应阅读：[岗位智能体前后台方案索引](./岗位智能体前后台方案/README.md)。现行口径为“一人可添加多个岗位智能体”，本文件中任何单岗位、无版本、无评测发布或旧后台岗位集描述均不得用于实现。

## 1. 这版先解决什么

本版先把三个问题讲清楚：

1. 个人侧和后台侧分别给谁用；
2. `role`、`soul`、`memory` 三部分怎样组织；
3. 一个人的唯一岗位怎样复用公共岗位集，并通过“我的补充”形成个人 role。

本版暂不设计“训练质量评测”。`memory` 也只确认一级入口和内容来源，不提前确定记忆期限、自动写入、遗忘及管理员可见规则。

## 2. 一句话产品结构

训练场不是两个系统，而是同一套数字分身训练能力的两个工作台：

- 个人侧：用户训练和管理自己的数字分身；
- 后台侧：组织查看全员建设状态、维护公共岗位集并进行内容治理。

后台能看到所有人的状态，不等于后台默认能看到所有个人内容。个人原始材料、`soul` 正文和 `memory` 内容默认不在管理列表中展开。

## 3. 三个核心对象

### role

`role` 表示数字分身在岗位上“负责什么、应该会什么、按什么规范工作”。本期明确：一个人只能启用一个岗位 role。

本版把公共岗位集定义为 `role` 的组织底座，主要包括：

- 岗位说明书；
- 岗位级能力地图（来自 C 大脑价值流和过程模型）；
- 岗位级知识地图（制度、规范、知识索引）；
- 脱敏并审核通过的历史任务和案例；
- 标准模板；
- 组织权限和强制规则。

个人可以复用公共岗位集，也可以在“我的补充”中增加职责补充、业务经验、知识资料、任务案例、常用模板和工作方法。个人修改只对本人的数字分身生效，不直接覆盖公共岗位集。

因此个人最终生效的 role 是：

`公共岗位集 + 个人补充 = 我的有效 role`

本期不提供个人向公共岗位集提交贡献或改进建议的能力，也不展示岗位版本、历史版本和恢复版本。

### soul

`soul` 沿用当前同事方案中的五类名称：

- 身份；
- 能力地图；
- 知识地图；
- 用户偏好；
- 指标达成。

其中：

- `role` 中的能力地图、知识地图是岗位级公共蓝图；
- `soul` 中的能力地图、知识地图是结合当前人员绑定关系、个人补充和权限过滤后的个人有效结果。

女娲负责通过访谈、个人材料和历史对话提炼心智模型、表达方式、判断规则和诚实边界。AI 提炼的内容先成为候选，必须由本人接受、修改或否认，不能直接写入有效 `soul`。

### memory

本版只保留三个现有名称：

- 会话记忆；
- 日志记忆；
- 任务状态。

页面仅用于展示信息架构和来源示例。具体哪些内容可进入长期记忆、保存多久、谁能看、怎样遗忘，后续单独讨论。

## 4. 个人侧页面

入口位于助理侧栏底部“训练数字分身”。

### 新用户首次创建

已训练用户可以在总览顶部点击“查看新用户状态”，演示首次进入时的真实空白态：

1. 系统先自动同步并确认组织身份；
2. `role / soul / memory` 以三张并列卡片出现，用户可以从任意一项开始，不设置步骤条和前后依赖；
3. 创建 role 时，可以“复用公共岗位库”或“C大脑抽取”；C大脑抽取会从已有岗位资料中提取职责、过程、知识和个人经验，并检查相似公共岗位集；
4. 创建 soul 时，可以“使用女娲蒸馏”或“上传 soul 文件”；暂时不创建时直接保持未创建状态，不需要专门执行“跳过”；
5. memory 可以独立建立入口，不受 role 和 soul 状态影响；
6. 每完成一项，只更新该项状态，其他两项仍可按需继续创建。

未创建的模块不阻塞助理使用：没有 role 时按通用助理工作，没有 soul 时使用默认工作方式，没有 memory 时只保留当前会话上下文。

新用户旅程和已训练状态属于同一个个人工作台，不拆成两套独立应用。后台仍然是另一套面向管理员的治理工作台。

个人侧包括：

1. 总览：展示本人的数字分身和 `role / soul / memory` 三个入口；
2. role：只展示当前唯一岗位，以及放大的“公共岗位集”和“我的补充”两个区域；
3. soul：展示五类内容、女娲访谈、训练材料和待本人确认的训练成果；
4. memory：暂时展示三个内容入口和来源示例；
5. 训练记录：展示岗位同步、个人修改、女娲访谈和内容确认历史。

总览中的任务看板与助理侧 A2A 会话使用同一份会话状态：分别展示多人通知、多人协作、单人协作和单人通知剧本。看板只按“进行中、待我确认、已完成”归类，不展示无法解释的百分比进度，也不设置“待处理”列；任务详情可直接进入对应 A2A 会话继续处理。

个人 role 启用后仍然可以编辑“我的补充”。公共岗位集由组织维护，个人只能查看，不能直接修改。

“我的补充”支持新增和编辑以下字段：

- 补充类型；
- 标题；
- 详细内容；
- 适用业务或工作场景；
- 相关附件；
- 生效状态。

本期不提供添加第二岗位、岗位清单、可调用岗位 Agent 清单、岗位贡献、岗位版本和历史版本入口。

### 公共岗位集资产查看

个人侧的公共岗位集为只读，但六类资产均可打开查看完整 Mock 内容：

- 岗位说明书：以正式文档形式展示岗位目标、核心职责、交付物、权限边界和上下游关系；
- 能力地图：以 C 大脑业务模型展示价值流，过程节点可点击查看输入、输出、负责人和当前岗位职责；
- 知识地图：以字段列表展示知识文件、类型、适用场景和内容摘要；
- 历史任务案例：展示标准项目情况，点击后以 Markdown 阅读项目背景、目标、约束、决策、交付物和经验教训；
- 标准作业模板：展示需求澄清、方案建议书、评审检查和交付验收等模板及正文结构；
- 岗位规则：展示组织维护的权限、确认、事实追溯和内容边界。

当前案例、文档、模型和模板均为前端 Mock，只用于让 Demo 看起来接近完整产品。

soul 页面顶部提供“继续女娲训练”“新增 / 导入”和更多操作。其中：

- 新增支持女娲蒸馏和上传 soul 文件；
- “重新创建 soul”位于更多菜单；
- 重新创建前先归档当前版本，旧版本仍可查看和恢复。

### 内容编辑规则

- 身份来自组织系统，个人侧只读；发现错误时提交反馈；
- 能力地图来自公共岗位集与 C 大脑过程模型，个人侧只读；如需修改，发起调整申请；
- 知识地图中的公共知识只读，个人补充内容可编辑；
- 用户偏好由本人维护，可以编辑；
- 指标达成中的目标、关注指标和行动计划可以编辑，实际完成值由业务系统同步，不允许手工改写。

## 5. 后台侧页面

入口位于助理侧栏底部“后台管理”，进入独立后台工作台。

### 数字分身管理

用于查看全员建设状态，包括：

- 人员和组织；
- 绑定的公共岗位集；
- 唯一岗位及 role 启用状态；
- 个人补充数量；
- soul 训练状态；
- memory 入口状态；
- 最近更新时间和异常。

这里默认只展示状态，不直接展示个人 `soul`、训练原文或 `memory` 正文。

### 岗位集管理

用于维护公共 `role`。岗位集首页采用卡片集合形式，支持按财务类、开发类、产品类和职能类筛选；不再展示公共岗位集数、覆盖人数、岗位资产和待完善岗位集等汇总指标。

点击岗位卡片后，当前主工作区下钻为岗位详情，左上角通过“返回岗位集合”回到卡片页。详情页不提供笼统的整体编辑入口，管理员点击对应资产模块后再维护该类内容。

“新建岗位集”只需从统一岗位目录中单选岗位名称，岗位分类和基础说明自动带出；不再填写公司级/部门级适用范围和负责人。新岗位集默认进入“整理中”状态。

岗位集包括：

- 岗位名称、岗位分类和基础说明；
- 岗位说明书；
- 能力地图；
- 知识地图；
- 历史任务案例；
- 标准模板；
- 强制规则和最近更新时间。

各资产模块的当前维护方式如下：

- 岗位说明书：仅提供“手动上传”和“知识库获取”两个模拟来源按钮，点击后直接展示一份完整的岗位说明书；
- 能力地图：由 C 大脑过程模型自动抽取，后台只能查看或重新抽取，不提供手动编辑；
- 知识地图：按文件维护，字段为知识文件、类型、适用场景和内容摘要；支持新增、编辑和删除。新增/编辑弹窗包含上传文件、类型单选和适用场景输入；
- 历史任务案例：提供两种 Mock 新增方式：

  - 对话抽取：管理员与案例抽取助手对话，右侧实时形成可编辑的结构化案例草稿，确认后模拟保存；
  - 上传 Markdown：模拟选择 Markdown 文件，展示字段识别、脱敏提醒和确认保存结果。

标准模板和岗位规则继续提供各自模块内的模拟维护入口。所有操作均为前端 Mock，不连接真实文件、知识库或 C 大脑接口。

岗位模块发生模拟修改后，详情页显示“有更新待同步”和受影响人数；点击同步后仅更新个人 role 的公共岗位内容，个人“我的补充”保持不变。本期以同步状态表达闭环，不引入岗位版本。

## 6. 当前原型中的权限原则

- 公共岗位集由组织维护，所有符合范围的人员可复用；
- 个人补充默认只对本人有效；
- 组织权限、强制制度和正式岗位职责不可被个人覆盖；
- 后台默认可看治理状态，不默认可看个人私有正文；
- 一个员工在本期只能绑定一个岗位 role。

## 7. 建议的原型演示顺序

1. 从助理侧栏进入“训练数字分身”，点击“查看新用户状态”；
2. 指出三张卡片是并列关系，然后故意先创建 soul，证明它不依赖 role；
3. 再创建 role，分别说明岗位库复用和 C大脑抽取两种入口；
4. 独立建立 memory 入口，观察三张卡片各自更新状态；
5. 切换回已训练状态，进入 `role`，说明一个人只有一个岗位，并演示新增、编辑和停用“我的补充”；
6. 进入 `soul`，说明身份、能力地图、知识地图、用户偏好和指标达成的不同编辑权限；
7. 从后台进入“数字分身管理”，说明管理员只看全员状态；
8. 进入“岗位集管理”，说明公共岗位资产由组织侧维护。

## 8. 后续仍需讨论

- `memory` 的写入、更新、遗忘、权限与保留期限；
- 训练质量怎样评测；
- 员工岗位发生变更时，怎样重新绑定公共岗位集并处理原有个人补充；
- 公共岗位集内容更新后，与个人补充发生冲突时怎样处理；
- 岗位版本、历史记录以及个人贡献能力是否在后续阶段引入；
- C 大脑、组织系统、知识库、女娲和业务系统之间的正式数据接口。
