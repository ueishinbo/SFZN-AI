# 历史讨论稿：后台管理与岗位 Agent 方案（V1.0）

> 状态：已被替代，保留日期：2026-09-09。本文的“岗位 Agent 模板 / 实例”分层属于早期探索，不是当前产品对象模型，也不作为实现依据。
>
> 当前应阅读：[岗位智能体前后台方案索引](./岗位智能体前后台方案/README.md)。现行口径只使用“岗位智能体”产品概念，不引入实例层；多岗位、评测发布和治理的当前规则以索引列出的总体方案、PRD、增量修订和验收记录为准。

## 1. 结论

后台与前台应当分离，但不是两套彼此割裂的 Agent 系统。

- **前台（个人工作台）**服务员工完成任务：员工通过自己的数字分身发起工作、查看结果和做最终确认。
- **后台（组织训练与治理台）**服务岗位负责人、事业群管理员和平台管理员：维护岗位能力、组织差异、授权边界、训练版本、发布范围和运行质量。

不要把“数字分身”定义为岗位，也不要让每个员工各自训练一套完整 Agent。建议采用四层模型：

```text
人员数字分身（谁在负责）
        │ 可绑定 0..n 个
        ▼
岗位 Agent 实例（在某事业群 / 部门如何干活）
        │ 基于
        ▼
岗位 Agent 模板（这个岗位的通用能力）
        │ 由
        ▼
组织资产与治理规则（知识、流程、工具、权限、评测）
```

人员数字分身负责个人身份、偏好、私有工作记忆、个人授权和最终责任；岗位 Agent 负责完成某一类岗位工作。一个员工可以兼任多个岗位，一个岗位 Agent 也可以被多名符合范围的员工绑定。

## 2. 为什么需要“模板 + 岗位实例”

同名岗位在不同事业群做法不同是正常现象，但通常不是完全不同的岗位。差异应该可配置、可追溯，而不是每个事业群从零训练一个“项目经理”。

| 层级 | 示例 | 放什么 | 谁维护 |
| --- | --- | --- | --- |
| 岗位 Agent 模板 | 项目经理 | 通用职责、能力框架、基础 SOP、通用提示词与评测基线 | 集团/平台岗位专家 |
| 岗位 Agent 实例 | 民机事业群·项目经理 | 本事业群流程、专属知识、业务系统工具、审批规则、指标 | 事业群管理员/岗位负责人 |
| 人员数字分身 | 张三 | 身份、工作偏好、个人授权、个人资料、私有记忆、当前绑定 | 员工本人 + 组织身份系统 |

例如，“项目经理”模板可以定义风险识别、计划编制、周报归纳等能力；“民机事业群·项目经理”实例再增加评审流程、型号资料库、项目系统和涉密规则。张三绑定该实例后，才获得在该范围内执行工作的能力。

**设计原则：**模板解决复用，实例解决组织差异，人员分身解决个体责任。任何一层都不应越权覆盖上一层的强制规则。

## 3. 核心对象与关系

### 3.1 人员数字分身

每名员工一个，始终绑定组织身份，而不是随岗位变动而销毁。它是前台的唯一入口和责任主体。

- 可绑定多个已发布且本人有资格使用的岗位 Agent 实例；
- 保存个人表达偏好、待确认事项、个人私有材料与工作记忆；
- 可设置每个岗位 Agent 的“默认 / 可用 / 暂停”状态；
- 不直接拥有组织级知识或工具权限，所有执行权限须经岗位实例和本人授权共同校验；
- 在高风险动作前，以“张三数字分身待张三确认”的形式回到前台。

### 3.2 岗位 Agent 模板

组织层可复用的岗位能力包，不直接给员工绑定和执行。它包括岗位说明书、能力地图、通用 SOP、基础知识目录、标准产物模板、通用评测集和不可覆盖的红线规则。

### 3.3 岗位 Agent 实例

某一组织范围内可运行的岗位 Agent，是员工真正绑定的对象。实例继承模板，并叠加事业群/部门规则。

- 适用范围：事业群、部门、项目或人员群；
- 业务资产：本地知识、流程、案例、输出模板；
- 工具与数据：可调用的业务系统、数据范围、操作级别；
- 运行规则：需确认动作、升级对象、可用时间、任务路由词；
- 发布状态：草稿、评测中、待发布、已发布、已停用。

### 3.4 训练包与版本

“训练”不是一个不可解释的大按钮，而是对岗位实例的可治理配置变更。训练包至少包含：知识、流程与规则、工具连接、示例任务、评测用例。保存产生草稿版本；只有通过评测和审批的版本可发布给人员分身使用。

## 4. 权限与责任边界

| 角色 | 主要动作 | 不能做什么 |
| --- | --- | --- |
| 平台管理员 | 管理全局模型策略、组织、角色、模板和审计 | 默认查看员工私有记忆正文 |
| 事业群管理员 | 建立/维护本范围岗位实例，配置人员绑定，发起发布 | 修改集团模板与跨事业群数据 |
| 岗位负责人 | 编辑训练资产、维护评测、查看脱敏运行反馈 | 自行发布高风险权限或查看个人私有内容 |
| 审批人 | 审核版本、工具权限、发布申请 | 修改训练正文 |
| 员工 | 维护个人分身偏好与私有材料、使用/暂停本人绑定 | 修改公共岗位资产或扩大权限 |

个人资料、对话原文和私有记忆默认归员工可见；后台只展示建设状态、风险告警和经脱敏/授权后的质量样本。涉及组织知识、系统写操作、敏感数据的变更，必须记录操作者、版本、审批和影响范围。

## 5. 后台信息架构

后台采用独立工作台，顶部始终显示当前组织范围与环境（如“民机事业群 / 正式环境”）。左侧一级导航建议如下：

```text
工作台
├─ 总览
├─ 岗位 Agent
│  ├─ 岗位模板
│  ├─ 岗位实例
│  └─ 训练与评测
├─ 数字分身
│  ├─ 人员分身
│  └─ 绑定管理
├─ 运行治理
│  ├─ 运行监控
│  ├─ 审批中心
│  └─ 风险与审计
└─ 组织设置
   ├─ 组织与角色
   ├─ 工具与数据源
   └─ 标签与字典
```

首期建议只完整建设：**总览、岗位实例、训练与评测、人员分身、绑定管理、审批中心**。运行监控和审计保留入口与基础列表，避免后台第一版过重。

## 6. 页面结构与关键交互

### 6.1 总览：回答“建设到哪里、有什么风险”

**页面结构**

- 顶部：组织范围选择、时间范围、全局搜索；
- 第一行：已发布岗位实例、已绑定人员、待审批版本、异常运行四个指标；
- 第二行：按事业群/岗位的覆盖率矩阵，点击格子进入对应实例或人员列表；
- 第三行：待我处理（发布审批、权限申请、评测失败）与风险提示；
- 右侧/底部：最近发布与运行质量趋势。

**交互**：指标和矩阵都必须可下钻，不做只有数字的看板。组织范围变化后，所有内容联动刷新；无权限的数据以汇总或不可见处理，而非显示空白。

### 6.2 岗位模板列表与详情：回答“通用岗位是什么”

**列表**：按岗位族、状态、负责人检索；卡片/表格显示模板名称、已派生实例数、最近版本、负责人和健康状态。点击进入详情，右上角仅给有权限的人“新建实例”。

**详情采用六个页签：**概览、职责能力、流程规则、知识与案例、工具权限、版本评测。资产均显示来源、负责人、更新时间和引用关系。模板变更不自动覆盖已发布实例：后台生成“可同步变更”提示，由实例负责人选择继承、局部覆盖或忽略。

### 6.3 岗位实例列表：后台的核心入口

**列表字段**：实例名称、基于模板、适用组织、状态、已绑定人数、当前版本、负责人、最近质量评分、更新时间。筛选包括事业群、岗位、状态、负责人和是否存在待处理变更。

**新建交互（四步轻向导）**

1. 选择岗位模板与适用组织；
2. 命名实例并确认负责人；
3. 选择继承资产，填写本地差异；
4. 保存为草稿，进入训练工作台。

不允许从空白新建可发布的岗位 Agent；确有新岗位时先建立模板，避免组织资产失控。

### 6.4 岗位实例详情：以“训练闭环”代替配置堆砌

详情头部显示名称、状态、版本、适用范围、负责人和“当前影响 N 名人员”。主内容分为：

```text
概览 | 训练资产 | 执行边界 | 评测 | 人员绑定 | 版本记录
```

- **训练资产**：知识、SOP、案例、输出模板四类卡片。每项可添加、编辑、下线；上传后先进入解析/脱敏校验状态，不直接生效。
- **执行边界**：配置允许的工具、数据范围和动作等级。写入、发送、下发、导出等动作必须选择确认策略：始终确认、条件确认或无需确认（仅低风险动作）。
- **评测**：展示覆盖的能力项、基准用例、最近结果和失败原因；支持从真实任务中脱敏沉淀候选案例，但须审核后加入评测集。
- **人员绑定**：显示已绑定人员与角色状态，可添加人员、暂停、解除绑定；解除前展示其个人材料和待办的处理提示，但不删除人员分身。
- **版本记录**：按版本展示变更摘要、评测、审批、发布人和影响范围；可一键回滚到已发布版本。

右上角主要操作随状态变化：草稿为“提交评测”，评测通过为“提交发布”，已发布为“创建新版本”。已发布版本禁止原地编辑，避免运行行为无审计地漂移。

### 6.5 训练与评测：把“能否上岗”说清楚

页面默认按岗位实例展示评测队列。进入某实例后为左右布局：左侧是能力项与用例目录，右侧是单次执行过程、结果、引用依据、得分和人工判定。

评测至少覆盖：事实正确性、流程合规、权限边界、输出质量、人工确认命中率。首期不追求一个笼统总分，发布门槛应写成可解释规则，例如“所有红线用例通过，流程合规率不低于 95%，关键输出由岗位负责人确认”。

### 6.6 人员分身：回答“谁绑定了什么、是否可用”

**列表字段**：员工、组织、分身状态、已绑定岗位实例数、默认岗位、待确认事项、最近活跃、风险状态。支持按组织、岗位实例、状态筛选。

**详情布局：**

- 左栏：人员身份、组织、分身启用状态、个人授权摘要；
- 中栏：已绑定岗位 Agent 卡片，可拖拽排序；第一张标记为默认岗位；
- 右栏：可见的治理状态（个人材料数量、记忆开关、待办、异常），不展示私有正文。

**绑定交互**：点击“绑定岗位 Agent”后，先选择当前组织范围内“已发布”且人员满足资格条件的实例；再设定使用状态、默认优先级和必要的个人授权；最后确认。若与既有绑定存在相同工具但不同权限，系统展示权限合并结果，默认取更严格的限制。

### 6.7 审批中心：避免训练资产直接进入生产

统一收纳版本发布、敏感知识、工具权限、人员批量绑定和高风险策略变更。列表显示申请对象、变更摘要、风险级别、影响人数、申请人、当前节点和时限。

审批详情固定展示“变更前 / 变更后 / 影响范围 / 评测证据 / 回滚方案”。审批人可通过、驳回或要求补充；不能在审批页直接修改训练内容，修改必须退回到草稿形成新版本。

## 7. 前台与后台的衔接

前台只有一个入口：员工的个人数字分身。用户无需理解模板、实例、版本等后台术语。

- 发起任务时，个人分身根据任务意图、当前组织范围、默认岗位和权限路由到一个或多个已绑定岗位 Agent；
- 无法唯一判断时，前台以简短选择卡让员工选择“以哪个岗位身份处理”；
- 多岗位协作时，个人分身负责汇总，岗位 Agent 的过程与引用记录保留在后台运行链路；
- 岗位实例更新后，不强制打断进行中的任务；新任务使用新版本，必要时由管理员设置生效窗口；
- 员工可在前台暂停某个岗位 Agent 或反馈结果质量，但不能自行扩大组织权限。

## 8. 首期范围与暂不做

### 首期必须闭环

1. 管理员从岗位模板创建事业群岗位实例；
2. 为实例添加知识、SOP、案例、模板和工具边界；
3. 运行基础评测并提交发布审批；
4. 将已发布实例绑定给一个或多个员工分身；
5. 前台按绑定关系路由任务，并对高风险动作请求本人确认；
6. 后台可追溯版本、绑定关系、运行状态和审批记录。

### 暂不纳入首期

- 自动从真实工作中无审批地学习和修改 Agent；
- 跨事业群共享私有知识或私有记忆；
- 自主解除/变更人员岗位绑定；
- 多 Agent 自主发起高风险外部操作；
- 复杂的组织矩阵权限、计费与容量分摊。

## 9. 需要领导确认的产品决策

1. 岗位 Agent 实例的最小组织范围是“事业群”还是允许细到部门/项目？建议：首期支持事业群和部门，不支持项目级常驻实例。
2. 一个员工最多绑定几个岗位 Agent？建议：首期上限 3 个，避免任务路由与权限解释失控。
3. 个人能否上传资料影响岗位 Agent？建议：可以作为“个人补充”影响本人调用效果，但不得直接进入公共岗位资产。
4. 哪些操作属于必须人工确认的高风险动作？建议先按发送、写入、下发、导出、跨系统操作五类统一定义。
5. 第一个验证岗位选谁？建议选流程清晰、知识可获得、低风险且可客观评测的岗位，而非一开始选择跨部门协调最复杂的岗位。

## 10. 建议的评审顺序

先用本方案讨论并确认“对象分层、事业群差异、人员多岗位绑定、权限边界”四项原则；确认后再画低保真页面流程，最后才制作可操作 Demo。这样 Demo 会验证已经达成共识的方案，而不是代替方案做决策。
